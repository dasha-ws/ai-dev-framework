# AI-Dev-Framework

ai-dev-framework помогает разрабатывать проекты с AI по понятному процессу – от идеи и требований до архитектуры, реализации, проверок и деплоя. Сейчас framework работает с [Claude Code](https://claude.com/product/claude-code).

Важные решения, требования и контекст проекта сохраняются прямо в репозитории. Поэтому не нужно каждый раз заново объяснять AI, что это за проект, что уже решили и что делать дальше.

С помощью framework можно разрабатывать Telegram-ботов, сайты, веб-приложения, API и backend-сервисы, админки и dashboard, Mini Apps, интеграции и автоматизации, а также мобильные и desktop-приложения. Framework задаёт процесс разработки, а не готовую реализацию или конкретный стек.

## Кому подойдёт

Тем, кто хочет разрабатывать свои проекты с AI – даже если раньше не работал с Claude Code или другими coding AI и не выстраивал полноценный процесс разработки.

Профессиональный опыт разработки не обязателен, это не no-code, но все непонятное можно отдельно разбирать с AI: в одном чате вести проект через framework, а в другом — задавать любые вопросы про термины, решения и то, что происходит на каждом этапе.

## Как это работает

Внутри framework есть skills для разных этапов разработки и специализированные AI-роли для проверки результата. Вам не нужно заранее разбираться, как они устроены: основные команды, назначение этапов и порядок работы описаны ниже.

В framework участвуют 11 AI-ролей. Десять из них – ревьюеры, которые независимо проверяют требования, архитектуру, технический дизайн, функциональное поведение, соответствие продуктовому замыслу, UX, качество кода, документацию, безопасность и инфраструктуру. `ui-designer` – отдельный помощник по дизайну для проектов, которым действительно нужен кастомный визуальный UI.

Это не автономная фабрика ПО. Каждый этап запускаете вы сами. Если нужное решение нельзя определить из проекта, framework спрашивает вас. Продуктовые и бизнес-решения остаются за вами.

- **Контекст внутри проекта.** `/init-project` добавляет в ваш проект небольшой контекст: продукт, архитектуру, разработку, инфраструктуру и, если применимо, UX-конвенции. Роутер подсказывает Claude Code, что читать для конкретной задачи.
- **Язык работы.** Перед началом framework спрашивает, на каком языке вам удобно работать. Спецификации и другие артефакты вашего проекта создаются на выбранном языке, а внутренние файлы и инструкции самого framework остаются на английском.
- **Спецификации как входные данные.** Требования и технический дизайн записываются в файлы до написания кода, и реализация следует им.
- **Skills.** Каждый этап – это skill, slash-команда с одной задачей: одни skills пишут спецификации, другие проверяют, отдельный skill реализует работу, а `/deploy` выполняет фактический деплой.
- **Агенты-ревьюеры.** Ревьюеров вызывают соответствующие skills для независимой проверки результата. Они не редактируют файлы вашего проекта, и обычно вы не вызываете их сами. Исключение – `ui-designer`: его вы вызываете самостоятельно, когда он действительно нужен.
- **Гейты.** Важная работа не переходит дальше, пока не прошла проверку своего этапа. Если гейт не пройден, работа возвращается тому skill, который отвечает за найденную проблему, после чего проверка запускается снова.
- **Одна ответственность – одно каноническое место.** У каждого правила и артефакта один владелец. Этот README – карта: подробные контракты лежат в [`skills/`](skills/), [`agents/`](agents/) и [`templates/`](templates/).

Skills не запускают друг друга. Каждый называет следующий шаг и останавливается. Результаты гейтов не хранятся в файлах: skill, которому нужен результат предыдущей проверки, опирается на текущий разговор или на ваше явное подтверждение.

## Требования

- Claude Code (подписка Claude Pro или выше).
- Windows с PowerShell — для установщика, который сейчас есть в этом репозитории (см. [Платформы и ограничения](#платформы-и-ограничения)).
- Локальная копия этого репозитория. Склонируйте или скачайте её как удобно. Сам установщик Git не требует.

## Установка

Здесь задействованы три разных места, и это не одна и та же папка:

- **Репозиторий фреймворка**: ваша локальная копия `ai-dev-framework`. Это только источник, из которого копирует установщик.
- **Установленный фреймворк**: копия в `%USERPROFILE%\.claude\`, которую на самом деле использует Claude Code (см. [Что устанавливается](#что-устанавливается)).
- **Ваш проект**: папка, которую вы хотите разрабатывать с фреймворком. Это отдельный каталог.

Запустите установщик один раз, одним из двух способов. Оба запускают один и тот же канонический установщик — [`scripts/install.ps1`](scripts/install.ps1).

**Двойной клик по `install.cmd`** в корне репозитория (папке `ai-dev-framework`, которую вы склонировали или распаковали). Это лишь небольшой лаунчер: он запускает `scripts/install.ps1` через `powershell.exe -NoProfile -ExecutionPolicy Bypass`, причём обход политики действует только для этого одного процесса, и оставляет окно открытым, чтобы вы прочитали результат. Он работает из любого места и не требует настройки.

**Или запустите скрипт напрямую**, из корня репозитория, в PowerShell:

```powershell
.\scripts\install.ps1
```

Если PowerShell блокирует запуск локальных скриптов, запустите его с переопределением политики выполнения только для этого процесса:

```powershell
powershell.exe -ExecutionPolicy Bypass -File .\scripts\install.ps1
```

Установщик не меняет политику выполнения PowerShell, не требует прав администратора и не использует сеть. Он проверяет источники до начала записи и останавливается с сообщением, если чего-то обязательного нет или путь назначения конфликтует. Он устанавливает только артефакты фреймворка и не трогает ваши проекты.

Установка завершена, когда установщик напечатал `ai-dev-framework installed.` и три пути назначения. После этого в репозитории больше не работают: переходите к своему проекту (см. [Быстрый старт](#быстрый-старт)). Копия репозитория снова понадобится только для обновления.

## Что устанавливается

| Артефакт | Расположение |
| --- | --- |
| Skills | `%USERPROFILE%\.claude\skills\<skill-name>\` |
| Агенты | `%USERPROFILE%\.claude\agents\<agent-name>.md` |
| Рантайм-шаблоны | `%USERPROFILE%\.claude\ai-dev-framework\templates\` |

Skills и агенты становятся доступны в Claude Code. Шаблоны — это рантайм-зависимости: их читают skills фреймворка (например, `/init-project` создаёт по ним файлы вашего проекта). Они не входят в ваш проект, а установщик не создаёт файлов проекта.

## Быстрый старт

1. Установите фреймворк (см. [Установка](#установка)).
2. Создайте или выберите папку своего проекта. Если новый проект нужно вести под версионным контролем, выполните в нём `git init` сами. `/init-project` не выполняет `git init` и работает без Git, но без Git ему не с чем сверять собственные изменения.
3. Откройте Claude Code в папке своего проекта, а не в репозитории `ai-dev-framework`. Skills фреймворка останавливаются, если их запустить внутри самого репозитория.
4. Запустите `/init-project` — первый шаг фреймворка. Он изучает проект и создаёт только недостающую структуру фреймворка из установленных шаблонов. Он не выдумывает факты и не перезаписывает существующие файлы. Всё, что он не может подтвердить, остаётся `TODO`, и спрашивает он только то, чего нет в проекте.
5. Продолжайте тем skill, который подходит к вашей ситуации:
   - новый продукт: `/product-spec`;
   - новая фича существующего продукта: `/new-feature-spec` — ему нужен достаточный контекст продукта (Product Specification или понятный существующий контекст проекта);
   - существующий проект, структуру которого нужно описать: `/architecture`.

Запуск установщика не запускает `/init-project`.

### Ожидаемый запрос разрешения

Фреймворк установлен вне вашего проекта, поэтому его шаблоны лежат в пользовательском каталоге. Когда skill, например `/init-project`, читает их, Claude Code может запросить разрешение на чтение пути вроде `%USERPROFILE%\.claude\ai-dev-framework\templates\...`. Это ожидаемо. Это не значит, что фреймворк читает другой ваш проект.

Перед тем как разрешить, проверьте путь: он должен быть внутри установленного каталога `ai-dev-framework`. Если запрос касается чего-то другого, например посторонней папки или другого проекта, не разрешайте, пока не поймёте, зачем это нужно.

## Типовые сценарии

Ниже — обычный порядок. Skill называет следующий шаг и никогда не запускает его за вас.

### Новый продукт

1. `/init-project`
2. `/product-spec` пишет Product Specification.
3. `/review-spec` проверяет её.
4. `/architecture` определяет начальную архитектуру. Ревью у `architecture-reviewer` skill организует сам.
5. `/tech-spec` пишет Technical Specification одного work item.
6. `/review-spec` проверяет Tech Spec.
7. `/build-feature` реализует.
8. `/test-feature` проверяет реализацию.
9. `/review-code` проверяет код.
10. `/update-docs` обновляет затронутую документацию и контекст проекта.
11. `/deploy-check` проверяет готовность к деплою. Сам он не деплоит.
12. `/deploy` выполняет фактический деплой проверенной версии. Это отдельный шаг, который вы запускаете сами, и он не нужен, если `/deploy-check` сообщает, что действий по деплою или релизу не требуется.

Шаги 5–12 работают с одним work item реализации за раз.

### Фича в существующем продукте

1. `/new-feature-spec` пишет Feature Specification.
2. `/review-spec` проверяет её.
3. Шаг с архитектурой условный:
   - если фича явно не требует изменений архитектуры, переходите сразу к `/tech-spec`;
   - если она явно требует существенного изменения архитектуры или её влияние неясно, сначала запустите `/architecture`. Он решает, нужно ли изменение, и если нет — вы продолжаете с `/tech-spec`.
4. `/tech-spec`, затем `/review-spec` для Tech Spec.
5. `/build-feature`, `/test-feature`, `/review-code`, `/update-docs`, `/deploy-check` и `/deploy`, если есть что деплоить, — как в сценарии нового продукта.

Если фича на самом деле меняет сам продукт (его общий замысел, основных пользователей или scope), сначала нужен `/product-spec`.

### Микроизменение

Действительно микроскопическая работа — например опечатка, тривиальная правка текста, очевидное исправление в одну строку или очень маленький изолированный багфикс — может обходиться без формальных спецификаций. `/build-feature` работает напрямую по вашему запросу с соразмерной реализацией и проверками разработчика. `/test-feature`, `/review-code`, `/update-docs` и `/deploy-check` применяются соразмерно, а не как одна обязательная фиксированная цепочка. Если вы запускаете один из этих гейтов, его обычные предусловия сохраняются: например, `/update-docs` требует актуальный PASS любого из предыдущих гейтов, через которые изменение реально прошло, `/deploy-check` всегда требует актуальный PASS `/update-docs`, а `/deploy` всегда требует актуальный PASS `/deploy-check`, чтобы выкатить изменение. Если изменение оказывается существенным, skills останавливаются и отправляют вас в обычный workflow.

### Деплой

PASS `/deploy-check` означает «готово к деплою», а не «задеплоено». Сам деплой — отдельный шаг, `/deploy`, и вы запускаете его сами.

- **Один target за запуск** (например, production, staging или один конкретный сервер). `/deploy` выкатывает ровно ту версию, которую прошёл `/deploy-check`, через механизм деплоя, который в проекте уже установлен. systemd — обычный поддерживаемый вариант, Docker и Compose по умолчанию не предполагаются, а сам `/deploy` механизм не выбирает и не меняет: это решение `/architecture`. Результат он проверяет так, как определяет этот механизм.
- **Первый деплой и обновление** существующего деплоя, а также read-only status и logs и rollback только по уже известной безопасной процедуре. Для status, logs и rollback новый `/deploy-check` не нужен.
- **Одно подтверждение и узкий scope.** Перед первым изменением на target `/deploy` показывает target, механизм, версию и что будет изменено, и ждёт вашего подтверждения. Переспрашивать каждую команду он не будет. Он остаётся в рамках текущего проекта и target, не трогает другие проекты и сервисы на том же сервере и не выполняет деструктивных действий над всем сервером без вашего отдельного решения.
- **Внешние credentials.** Когда нужен credential, `/deploy` объясняет, что это, зачем он нужен, где его получить, куда настроить и как безопасно проверить. Значения секретов вы вводите сами, не в чате. В контексте проекта они не сохраняются и не коммитятся, а содержимое приватных ключей никогда не запрашивается.
- **Состояние деплоя.** После проверенного деплоя или rollback `/deploy` записывает подтверждённое состояние этого target в `infrastructure.md`: текущие факты по каждому target, без значений секретов и без истории деплоев.

## Skills

Каждый `SKILL.md` в [`skills/`](skills/) — полный контракт своего skill.

| Skill | Назначение |
| --- | --- |
| `/init-project` | Готовит проект: создаёт недостающий контекст фреймворка, рабочие папки и короткий корневой `CLAUDE.md`, не выдумывая фактов и не перезаписывая файлы. |
| `/product-spec` | Пишет или обновляет Product Specification через короткое интервью и синхронизирует `product.md`. |
| `/new-feature-spec` | Пишет или обновляет Feature Specification для одной фичи или значимого изменения существующего продукта. |
| `/architecture` | Владеет долговечной архитектурой: описывает существующую систему, проектирует начальную архитектуру или определяет влияние проверенной Feature Spec на архитектуру. |
| `/tech-spec` | Пишет Technical Specification одного work item: как согласованные требования реализуются внутри согласованной архитектуры. |
| `/review-spec` | Независимый PASS/FAIL-гейт для одной Product, Feature или Technical Specification. |
| `/build-feature` | Реализует один work item в коде вместе с тестами и проверками разработчика, а также исправляет замечания поздних гейтов, относящиеся к реализации. |
| `/test-feature` | Гейт проверки после реализации: независимая функциональная проверка, проверка соответствия продуктовому замыслу и, для пользовательской части, UX-проверка реализованного поведения. |
| `/review-code` | Гейт качества кода после успешного `/test-feature`. |
| `/update-docs` | Обновляет документацию и допустимый контекст проекта, затронутые принятой реализацией, и организует их ревью. «Изменений не требуется» — допустимый результат. |
| `/deploy-check` | Финальный гейт готовности по безопасности и инфраструктуре для одной цели деплоя. Он проверяет готовность и никогда не деплоит. |
| `/deploy` | Выполняет фактический деплой проверенной версии на один target через уже установленный в проекте механизм доставки, проверяет результат и записывает подтверждённые факты о текущем состоянии деплоя. Также status, logs и rollback по известной безопасной процедуре. |

## Агенты

Агенты — это специализированные роли, которые используют skills. Они лежат в [`agents/`](agents/).

### Агенты-ревьюеры

Ревьюеров вызывает их skill-владелец, и они рекомендуют результат. Итог определяет skill.

| Агент | Вызывается из | Проверяет |
| --- | --- | --- |
| `requirements-reviewer` | `/review-spec` | Product и Feature Specification. |
| `tech-spec-reviewer` | `/review-spec` | Technical Specification. |
| `architecture-reviewer` | `/architecture` | `architecture.md`. |
| `qa-reviewer` | `/test-feature` | Функциональное поведение реализации. |
| `product-reviewer` | `/test-feature` | Реализацию относительно утверждённого продуктового или фичевого замысла. |
| `ux-reviewer` | `/test-feature` | Пользовательский опыт относительно утверждённых UX- и UI-ожиданий, для пользовательской части. |
| `code-reviewer` | `/review-code` | Качество кода. |
| `docs-reviewer` | `/update-docs` | Влияние на документацию и её обновления. |
| `security-reviewer` | `/deploy-check` | Готовность по безопасности для цели деплоя. |
| `infrastructure-reviewer` | `/deploy-check` | Готовность инфраструктуры и деплоя для цели деплоя. |

### ui-designer

`ui-designer` — самостоятельный помощник по дизайну, а не ревьюер. Вы вызываете его осознанно, до реализации, для работы, которой действительно нужен кастомный визуальный UI, например сайта, веб-приложения, дашборда или мобильного приложения. Он предлагает визуальное и интеракционное направление в виде передачи только в разговоре, и это остаётся предложением, пока вы его не утвердите. PASS или FAIL он не выдаёт, `/test-feature` его никогда не вызывает, и ни один skill им не владеет. Многим проектам он не нужен вовсе: у обычного Telegram-бота, API или библиотеки нет кастомного визуального UI, который нужно проектировать.

## Структура целевого проекта

После `/init-project` в вашем проекте есть:

```
CLAUDE.md
.claude/
  skills/
    project-context/
      SKILL.md
      context/
        product.md
        architecture.md
        development.md
        infrastructure.md
        ux-guide.md        (только если у проекта есть пользовательский интерфейс, пользовательские сценарии или пользовательский контент)
  product/
    product-spec.md        (нестартовая заглушка)
  work/
    completed/
```

- `CLAUDE.md` — короткая точка входа, которая направляет Claude Code к контексту проекта.
- `.claude/skills/project-context/` — контекст проекта: роутер и долговечные файлы контекста.
- `.claude/work/` хранит спецификации текущей работы, по одной папке на work item, а `completed/` предназначена для завершённых. Feature и Technical Specification создаются там позже своими skills, как `<name>/feature-spec.md` и `<name>/tech-spec.md`. Сразу после инициализации их нет.

Шаблоны фреймворка в эту структуру не входят. Они остаются в каталоге установки.

## Спецификации и контекст

| Артефакт | Владеет | Пишет |
| --- | --- | --- |
| Product Specification, `.claude/product/product-spec.md` | Требованиями уровня продукта. | `/product-spec` |
| Feature Specification, `.claude/work/<name>/feature-spec.md` | Требованиями одной фичи или изменения. | `/new-feature-spec` |
| Technical Specification, `.claude/work/<name>/tech-spec.md` | Тем, как реализуется один work item. | `/tech-spec` |
| `architecture.md` | Долговечной согласованной архитектурой. | `/architecture` |
| Остальные файлы контекста | Короткими долговечными фактами и конвенциями: дайджест продукта, разработка, инфраструктура, опциональный UX. | Создаются `/init-project`. `/product-spec` синхронизирует `product.md`, `/update-docs` может синхронизировать описательные факты, а `/deploy` записывает подтверждённое состояние деплоя target в `infrastructure.md`. |

Код показывает, что реализовано сегодня. Он не определяет, что продукт должен делать. Когда спецификация, контекст проекта и код расходятся, расхождение устраняется в источнике-владельце, а не лечением симптомов.

## Обновление

1. Обновите локальную копию репозитория (pull или скачайте новую версию).
2. Снова запустите установщик, как в разделе [Установка](#установка): в Windows двойным кликом по `install.cmd` либо напрямую `scripts/install.ps1` из PowerShell. Оба способа используют один и тот же канонический `scripts/install.ps1`.

Установщик обновляет из копии каждый текущий skill фреймворка и дерево рантайм-шаблонов, заменяя их установленные копии, так что правки внутри этих копий будут перезаписаны. Он перезаписывает файлы текущих агентов фреймворка. Другие skills, другие агенты и другая конфигурация Claude остаются нетронутыми. Установщик не хранит записи о том, что ставил раньше, поэтому не может удалить skill или агента, которых новая версия больше не содержит. Такие остатки удаляйте вручную.

## Платформы и ограничения

- Автоматический установщик из этого репозитория работает только в Windows (PowerShell). В репозитории нет `install.sh` или другого установщика для macOS и Linux. Это относится только к установщику: target деплоя — то, что использует установленный в проекте механизм, например удалённый Linux-сервер.
- Команды удаления и управления версиями нет. Обновление — это повторный запуск установщика.
- ai-dev-framework не заменяет ваши продуктовые решения, зависимости проекта, инфраструктуру деплоя и собственные тесты и инструменты проекта. Skills спрашивают у вас решения, которые не могут вывести сами, `/deploy-check` проверяет готовность и не деплоит, а проверка следует тем проверкам и процедурам, которые определяет ваш проект или установленный в нём механизм деплоя.
